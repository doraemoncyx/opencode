# CLI and TUI development guide

- Use `@opencode/client` and the location-scoped data in `packages/tui/src/context/data.tsx`.
- Preserve established TUI behavior unless the task intentionally changes it.
- `opencode serve` without `--service` takes its basic-auth password from `OPENCODE_PASSWORD`; the `password` in `<config>/opencode/service.json` applies only to service mode, so reusing it for a locally spawned serve returns 401.
- Source (`bun packages/cli/src/index.ts serve`) vs compiled binary: same steady-state request latency, but startup is ~1.7s vs ~0.6s and RSS ~196MB vs ~127MB, because workspace exports resolve to `./src/*.ts` and every module is transpiled and resolved at runtime instead of shipping bundled minified bytecode. Keep `--smol` in both runs; it is what makes GC behavior comparable.
- A long-lived source-mode `serve` burning exactly one core on a single native thread while JS stays at ~2% and request latency is unaffected is a **Bun inspector bug, not a bundling difference**: `Profiler.setSamplingInterval(<= 500)` followed by `Profiler.start`/`stop` leaves a native thread spinning at ~100% of one core until the process restarts (1000µs and default leave ~6%; no sampling leaves 0%). `start_dev_server.py` defaults to `--interval 200`, so every sampling run with `--keep` pins a core. The inspector profiler shows nothing because the CPU never enters JS; use per-thread CPU deltas (`psutil` `threads()`) or a native stack walk instead.
- Task Manager's "% CPU" is normalized across all logical cores: 5% on this 20-core box is 100% of one core. Divide by `psutil.cpu_count()` before comparing against a single-process CPU budget.
- A source-mode `serve` returning `HTTP ERROR 500` on `/` with `Web UI assets are missing from the CLI build` is channel-driven: `virtual:opencode-app-assets` only exists in the bundle, and `app-assets.ts` used to fall back to `packages/app/dist` only when `OPENCODE_LOCAL` (`channel === "local"`). Running source with a non-local channel is normal — `start_dev_server.py` pins `latest` so the DB and service registration match the installed client — so `app-assets.ts` now tries `packages/app/dist` either way and keeps the old error only when that directory is absent. `packages/app/dist` must be built (`bun run build` in `packages/app`) for the web UI to appear; the CLI itself never needs rebuilding for a `.ts` change in source mode.
- The same source-mode web UI 404s every `/_assets/*.js` while `/` still renders: `FileSystem.readDirectory(root, { recursive: true })` reports OS-separated paths, so on Windows the asset map's keys were `_assets\foo.js` while the server looks up slash-separated URL paths. Normalize the key when building the map, not at lookup.
